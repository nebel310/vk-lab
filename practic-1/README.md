## 1. Что сделано

Развёрнут локальный **Lakehouse** на стеке **MinIO → Lakekeeper → Trino → Spark**, реализован полный цикл ELT (Bronze → Silver → Gold) и проведён бенчмарк колоночных форматов **Parquet** и **ORC** с различными кодеками сжатия.

Покрытие задания:

| Пункт задания | Где реализовано |

| Развёртывание локального Lakehouse | `docker-compose.yml`, `catalog/`, `create-warehouse.json` |
| Загрузка сырых данных в Parquet и ORC с 3+ кодеками | `spark_jobs/spark_bench.py` |
| ELT: очистка, нормализация, обогащение | `spark_jobs/elt_pipeline.py` |
| Построение агрегированной витрины для BI | `spark_jobs/elt_pipeline.py` (Gold) |

Использованы два независимых набора данных:

Генерируется встроенным коннектором Trino `tpcds`. Используется для бенчмарка в Trino/Iceberg.

Генерируются в Spark через `spark.range` со случайными и модульными колонками. Используются для бенчмарка Spark и для ELT-пайплайна.

## 4. ELT-пайплайн (медальонная архитектура)

Реализован в `spark_jobs/elt_pipeline.py` на 10 млн строк.

### 4.1. Bronze — сырьё как есть

- Генерация 10 млн строк с **намеренно подмешанным мусором**:
  - дубликаты по `sale_id` (~1%);
  - отрицательные и нулевые `quantity`;
  - `NULL` в `customer_email` (~5%);
  - ненормализованные email (нижний регистр не гарантирован).
- Запись: **Parquet + SNAPPY**.

**Результат:** 10 099 715 строк, 233,9 МБ, 25 файлов, запись 6,6 с.

### 4.2. Silver — очистка, нормализация, обогащение

Шаги:

1. **Дедупликация** по `sale_id` (`dropDuplicates`).
2. **Фильтрация мусора**: `quantity > 0`, `unit_price > 0`, `customer_email IS NOT NULL`.
3. **Нормализация**: приведение `sale_ts` к timestamp, `customer_email` к lowercase и trim.
4. **Расчётные поля**: `gross_amount`, `discount_amount`, `net_amount`.
5. **Обогащение**: `JOIN` со справочником магазинов `stores` (12 магазинов, города, регионы).

- Запись: **ORC + ZSTD**.

**Результат:** 8 074 103 строки (отброшено **20,1 %** мусора), 184,1 МБ, 9 файлов, запись 19,8 с.

## 5. Бенчмарк форматов и кодеков

### 5.1. Методика

Для каждого сочетания **(формат, кодек)** измерялись:

1. **Размер файлов** — суммарный объём файлов данных в MinIO.
2. **Время записи** — wall-clock от старта `write.save()` до завершения.
3. **Скорость агрегации**:
   - `agg_first` — первый `GROUP BY` (холодный кэш, чтение с S3);
   - `agg_next` — среднее второго и третьего прогонов (прогретый кэш Trino/Spark).

Тестировались комбинации:

- **Parquet**: SNAPPY, ZSTD, GZIP, NONE

## 6. Обоснование выбора

### 6.1. Почему ZSTD

ZSTD — оптимальный баланс «размер ↔ скорость»:

- **В PyArrow:** Parquet+ZSTD сжал до 18,67 МБ — лучший результат среди всех Parquet-вариантов. При этом запись 1,38 с — на уровне SNAPPY (1,12 с).
- **В Trino/Iceberg:** ORC+ZSTD дал 0,0018 ГБ — минимальный размер из всех. Агрегации 0,125 / 0,124 с — самые быстрые.
- **В Spark:** ORC+ZSTD пишется за 7,45 с (самое быстрое среди ORC) и даёт 320 МБ — второй результат после Parquet+GZIP.

ZSTD используется как **дефолт в Iceberg** — значит, экосистема оптимизирована именно под него.

### 6.2. Почему GZIP-9 не окупается

- PyArrow: Parquet+GZIP-9 пишет **30,01 с** против 1,38 с у ZSTD — **в 21 раз медленнее**, а размер лучше всего на 27 % (18,67 vs 25,77 МБ).
- Spark: Parquet+gzip пишет 18,37 с против 10,34 с у zstd при почти одинаковом размере (296 vs 306 МБ).
- Trino: Parquet+GZIP — 3,45 с против 1,76 с у ZSTD.

Классика: **максимальный уровень редко окупается**.

### 6.3. Почему SNAPPY проигрывает в Spark

Snappy быстрый по CPU, но в нашем случае узкое место — **S3A и сеть**, а не кодек. Поэтому snappy пишет 15,2 с (Parquet) и 10,15 с (ORC) — медленнее zstd. Это иллюстрирует принцип «подбирай кодек под профиль нагрузки, а не по общим советам».

### 6.4. ORC vs Parquet

- **Parquet** лучше сжимает **десятичные числа и длинные строки** (dictionary encoding, delta-кодирование).
- **ORC** лучше работает с **целочисленными ключами и RLE-повторами** (у нас `store_id` повторяется каждые 12 строк).
- В Trino/Iceberg **ORC+ZSTD показал лучшие цифры по всем метрикам**.
- В Spark результаты сопоставимы: ORC+ZSTD 320 МБ / 7,45 с vs Parquet+ZSTD 306 МБ / 10,34 с.

### 6.5. Trino vs Spark

- **Trino** эффективнее для **интерактивных агрегаций** на небольших и средних данных: агрегация 0,1–0,4 с против 0,3–1,4 с у Spark.
- **Spark** выигрывает на **ETL-нагрузках** (генерация, джойны, очистка) и на очень больших объёмах, где нужна распределённая запись.
- На нашем объёме **Spark быстрее пишет** (7–15 с против 1–20 с в Trino, но это разные данные и разное число партиций), а **Trino быстрее агрегирует**.

### 6.6. Эффект кэша

Во всех бенчмарках **первая агрегация в 1,3–2,5 раза медленнее последующих**:

- Trino: `0,169 → 0,129` (Parquet+SNAPPY), `0,410 → 0,155` (Parquet+NONE).
- Spark: `1,394 → 0,714` (Parquet+snappy), `0,871 → 0,406` (ORC+snappy).

Причина — прогретый **метаданный кэш Lakekeeper + файловый кэш Trino/Spark**. На реальных объёмах (десятки ГБ) разрыв был бы больше.

## 8. Выводы

1. **Сжатие всегда включать.** Даже самые быстрые кодеки (Snappy, LZ4) дают 2–4-кратную экономию размера, а по времени записи в Spark они не медленнее «без сжатия» — узкое место в S3A, а не в CPU.

2. **ZSTD — оптимальный дефолт.** Он даёт лучший баланс: близкий к GZIP размер и близкую к Snappy скорость. Это подтверждено на трёх платформах (PyArrow, Trino/Iceberg, Spark).

3. **Максимальный уровень сжатия (GZIP-9) не окупается.** В 20+ раз медленнее записи при выигрыше в размере ~25 %. Оправдан только для «холодных» архивов, где важна каждая копейка хранения и данные редко читаются.

4. **ORC+ZSTD в Iceberg — победитель** по совокупности всех метрик: минимальный размер, минимальное время записи, минимальное время агрегации.

5. **Кэш даёт ускорение в 1,3–2,5 раза** при повторных агрегациях. Первый запуск всегда «холодный» — прогревает метаданные и файловые кэши.

6. **Выбор движка зависит от задачи.** Trino — для интерактивной аналитики, Spark — для ETL и очень больших объёмов.

7. **Медальонная архитектура** (Bronze → Silver → Gold) даёт изоляцию слоёв: сырьё никогда не перезаписывается, вся логика очистки и обогащения централизована в Silver, витрины Gold пересобираются за секунды.

## 10. Как воспроизвести

```bash
# 1. Поднять стенд
cd lakehouse
docker compose up -d

# 2. Дождаться готовности (30–60 с)
docker compose ps

# 3. Скачать JAR'ы и запустить бенчмарк Spark
docker compose exec spark /opt/spark/bin/spark-submit \
  --driver-memory 3g \
  --packages org.apache.hadoop:hadoop-aws:3.3.4,com.amazonaws:aws-java-sdk-bundle:1.12.262 \
  /jobs/spark_bench.py

# 4. Запустить ELT-пайплайн
docker compose exec spark /opt/spark/bin/spark-submit \
  --driver-memory 3g \
  --packages org.apache.hadoop:hadoop-aws:3.3.4,com.amazonaws:aws-java-sdk-bundle:1.12.262 \
  /jobs/elt_pipeline.py

# 5. (Опционально) Запустить Jupyter-ноутбуки
uv venv --python 3.12
uv pip install pyarrow boto3 pandas numpy matplotlib requests jupyter
.venv\Scripts\Activate.ps1
jupyter notebook
```

**Требования:** Docker Desktop (Windows 10/11 или macOS), ≥ 8 ГБ RAM (Docker выделено ≥ 4 ГБ), свободные порты 9000, 9001, 5432, 8181, 8080.
